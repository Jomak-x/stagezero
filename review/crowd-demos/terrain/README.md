# Hikari station terrain audit

The [Scene3 proxy](station-proxy.scene3.json) transcribes the **east** terrace and all six stair boxes from [`EnvironmentScene.ts`](../../../studio_client/src/environments/EnvironmentScene.ts) `station()` (lines 639–642). Each step is 15 m wide and 0.5 m deep, centred at X=41, Z=`-0.4 - 0.5×step`, with bottom Y=0 and top Y=`0.25 + 0.25×step`. The terrace is the actual 15×1.5×15 m box centred at (41, 0.75, -11). A limited explicit Y=0 plaza slab supplies the corridor's rendered level support. This is a **hand-authored geometry proxy**, not a reconstruction from an image, the whole station environment, or a learned scene model.

The [offline comparison](comparison.json) uses one actor from (32, 0, -8) to (50, 0, -8). A conventional Y=0 straight path has collision or support failures at **161/181** sampled points as it cuts through the raised terrace. The geometry planner returns a **31.20 m** supported route versus the straight path's **18 m**, with **zero** failures over its 8 vertices and 315 swept samples. It goes around the terrace's front and uses the first rendered 0.25 m tread on the crosswise segment. This demonstrates actual surface and body-proxy avoidance at this location; it does not prove native gait, full skinned-mesh clearance, visual quality, or crowd interaction.

The station stairs are **not presently usable for a scripted ascent**. Their box risers grow to 1.5 m thick; `scene_interaction_geometry._tread_steps` excludes boxes taller than 0.5 m, so no stair flight is detected. The command `walk up east station stairs` resolves the authored object but `plan_command` rejects with `east-stairs has no unambiguous rendered stair flight` before generation. There is also a 0.35 m horizontal unsupported gap between the last stair box (back edge Z=-3.15) and the terrace (front edge Z=-3.5). The exact geometry cannot be called a connected station staircase. The Y=0 support beneath that gap does not make the 1.5 m elevated gap traversable.

The exact station world coordinates also exceed the Core terrain command's ±25 m route bound (`core_terrain_navigation.py:335`). Existing temple/industrial native archives were generated for other scenes and cannot certify a station take. There is therefore **no accepted native station generation, Human17 display solve, or 17-joint display JSON** in this evidence. A later full-motion trial would first need an intentionally translated stage and a connected shallow stair asset, followed by fresh native generation and contact validation. It should be described as a modified station test, not this exact rendered stair geometry. No GPU worker was used or restarted here.

## Koma kiosk: actual opt-in Core attempt

A separate [kiosk Scene3 proxy](kiosk/scene3.json) transcribes the four solid boxes of the west **Koma Express** kiosk from `EnvironmentScene.ts:663–669`, including the `Builder.local(-22, 4, +0.25 rad)` transform. Its bounded Y=0 plaza slab supplies only the local route corridor. The kiosk's text/sign plane is decorative and omitted. The kiosk is an authored geometry proxy, not vision-derived layout. The one-actor route begins at (-22, 0, 1) and aims for (-22, 0, 7). A straight path has **123/161** body-envelope collision samples. [Preflight](kiosk/preflight.json) planned a 9.23 m detour through X=-18.25 in exactly **six** Core horizons.

The existing authenticated Core worker at `127.0.0.1:8769` was healthy and idle. Its older HTTP schema first rejected the new client's optional terrain-height fields before any GPU work. Because this route is flat, the [reproducible trial script](../../../experiments/crowd_demo_kiosk_motion.py) retried with only a zero scene-height origin and constant neutral 0.95 m root-height hints omitted; XZ route, scene, and validation were unchanged. One six-horizon generation completed in **7.62 s**, producing [240 native frames](kiosk/native.npz) with exact 330-channel feature history. [Native completion evidence](kiosk/native-ready.json) shows 4.9 mm arrival error, 3.0 cm root-height error, and passing native root/major-body checks. This is real opt-in Core output, with the original first and second [rejection records](kiosk/initial-http-rejection.json) and [display rejection](kiosk/rejection.json) retained.

The display solve rejected; **there is no accepted Human17 display JSON**. Its first/worst failed sample is frame 173, right sole at (-19.20994, 0.11041, 5.51197). The foot lies below the kiosk counter top at Y=1.11, while the authored plaza floor is Y=0. The solver's 1.0 m upward support search chooses that overhead counter and reports 0.9996 m sole penetration. The [frame audit](kiosk/audit.json) confirms the sole sample is outside the solid at its own height; both native and display root positions still sample the plaza floor. A CPU-only diagnostic restricting sole support search to 0.35 m removes that false penetration, but [the alternate solve](kiosk/bounded-support-retry.json) still violates the unchanged 35°/frame leg-rotation limit at **35.189°/frame**. A separate [body sweep](kiosk/body-audit.json) finds a Rig17 limb intersecting the actual kiosk at frame 167. The valid native route therefore cannot be presented as a passing assisted display under current constraints. No GPU work was repeated after the six saved horizons. The CPU-only support experiment did not modify product code or relax acceptance thresholds.

The kiosk preflight is also checked by the offline test suite, which now passes **5/5** tests. Use the saved native archive for any later display-only diagnosis; a new Core request is unnecessary.
