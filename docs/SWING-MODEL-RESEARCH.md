# Swing, carry, landing, and kiss: model and rig decision

Checked 2026-09-26 against the running Pod and three fresh, unmodified ARDY Core outputs. The practical stack for this sequence is **ARDY Core for native body articulation, an authored rope/flight and two-body contact controller for world motion, and an independent face rig for the kiss**. A text prompt by itself did not produce the required aerial travel or reliable hand contact in the bounded probe. These are measured limitations of these three seeds, not a claim that no seed or added native condition could succeed.

## Fresh native evidence

The [probe](../experiments/swing_model_probe.py) called the existing authenticated realtime service on port 8769. It loaded no new checkpoint, created no Pod, and saved the exact service outputs as [canonical Core clips](../assets/swing-motion/manifest.json): 80 frames each, 20 fps, 27 joint positions `[T,27,3]`, global proper rotations `[T,27,3,3]`, and native features `[T,330]`. Two 40-frame chunks were returned per case. Arrays were finite and the rotation determinants differed from one by at most about `1e-6`. NPZ metadata preserves prompt, seed, service request ID, and chunk provenance. The file manifest includes SHA-256 hashes.

| Prompt case | Root horizontal range | Root vertical range | Right hand >10 cm above right shoulder | Interpretation |
| --- | ---: | ---: | ---: | --- |
| Swing, right hand overhead (seed 1201) | 0.234 m | 0.122 m | 80/80 frames | Useful native upper-body and grip-like silhouette; no aerial arc. |
| Hang and reach (seed 1202) | 0.091 m | 0.048 m | 0/80 frames | Text missed the intended overhead hold in this seed. |
| Land then carry (seed 1203) | 0.172 m | 0.586 m | 3/80 frames | Native bend/jump/settle variation, but there is no second person in the output. |

The current service exposes native root waypoints and a trusted constraint hook, but Core remains a **single-person checkpoint**. Two simultaneous Core samples share a clock but do not sense one another. The sequence needs a scene controller with a rope anchor, pendulum path, carrier/passenger attachment, foot-ground contact, and explicit hand/torso/head goals. Use the saved swing clip as an articulation source; the authored physical path must own the pelvis trajectory. Use a separate landing transition and hold state, then solve the carrier's arm contacts and the passenger's supported pose in world coordinates. The head/neck pose can aim the faces; final mouth-to-mouth alignment needs an authored target and facial controls. NVIDIA describes Core as 27 joints, 20 fps, 40-frame horizons with text and sparse kinematic constraints; it does **not** claim awareness of objects or a facial channel. [ARDY Core model card](https://huggingface.co/nvidia/ARDY-Core-RP-20FPS-Horizon40), [ARDY source](https://github.com/nv-tlabs/ardy), [local native runtime](../interaction_runtime.py).

Native ARDY constraints should be used where feasible, especially root waypoints and hand keyframes, but they are soft generative conditions and do not enforce rope tension, pair collision, grip force, or exact lip contact. Deterministic physics and IK must accept or correct each generated horizon before display. For a live interaction, generate a new Core horizon asynchronously on a command, then blend **joint rotations** into the currently valid constrained pose while maintaining fixed bone lengths and contact anchors. Never make a pose clip's small text-generated root displacement drive the web swing. The saved clip provides a verifiable source for that blend; the resulting staged pose is a hybrid animation, not a wholly model-generated stunt.

## Candidate models and why this stack wins now

- **ARDY Core Horizon40** is already loaded and measured here. Its human skeleton has Head and Neck and supports prompt changes plus keyframe/waypoint conditions. Its model card says commercial or noncommercial use under the NVIDIA Open Model Agreement. It has no lip, eyelid, jaw, gaze, or blendshape tracks. [Model card](https://huggingface.co/nvidia/ARDY-Core-RP-20FPS-Horizon40).
- **InterGen** is the existing paired research adapter and can produce two coordinated human motion streams. Its official repository licenses the work under CC BY-NC-SA 4.0, and it is a poor basis for a broadly deployable prototype without separate rights. The existing service labels paired output as research. It also does not supply face animation or a web/rope physics input. [Official repository and license](https://github.com/tr3e/InterGen).
- **Kimodo SOMA RP v1.1** is a human-body alternative for later motion-quality comparison, with a different runtime and retargeting path. It cannot simply replace the live ARDY Core service and still needs external two-person contact and face animation. [Official Kimodo quick start](https://github.com/nv-tlabs/kimodo/blob/main/docs/source/getting_started/quick_start.md).

The vendored ARDY code and `CoreSkin` implementation plus `cskel27/skin_standard.npz` are tracked in the upstream Apache-2.0 repository. The Core checkpoint has its **separate** NVIDIA Open Model Agreement. `CoreSkin` is a useful neutral pose reference, not a finished Spider-Man or MJ asset. [ARDY license notes](https://github.com/nv-tlabs/ardy#license), [checkpoint terms](https://huggingface.co/nvidia/ARDY-Core-RP-20FPS-Horizon40). The local `assets/BONES-SEED-LICENSE.md` is a **dataset** agreement with separate eligibility and attribution conditions; no raw BONES-SEED dataset was used by this probe. Avoid importing InterGen's research-only source/weights into the finished runtime. The Microsoft TRELLIS image checkpoint is listed as MIT; its repository says most code and models are MIT, while certain submodules have separate licenses. [TRELLIS model card](https://huggingface.co/microsoft/TRELLIS-image-large), [repository license section](https://github.com/microsoft/TRELLIS#%EF%B8%8F-license).

## Character assets and facial layer

The original workspace has a locally built Spider-Man costume GLB at ignored `.runtime/character-quality/spiderman-local.glb`; `character_costume.py` baked a fitted hood, lenses, web pattern, and emblem over a generated textured human. It is **not** an off-the-shelf downloaded character. Its existing `character_actor.py` skin weights follow G1 joints, so it needs an explicit Core27 fit or a new authored Core compatible rig before using these clips. Merely changing the motion array size cannot animate that GLB. Those files were inspected in the original workspace (`character_costume.py`, `character_actor.py`, and `docs/CHARACTER-VERIFICATION.md`); they are not copied or modified in this isolated prototype.

For a credible close-up, give both characters individually controlled head and neck orientation, eyes/eyelids, jaw, and mouth shapes. The source Spider-Man hood has opaque lenses and no face rig; a kiss close-up needs a separately authored exposed-face or lifted-mask variant with skin material and at least jaw/lip morph targets. MJ needs a textured human mesh with stable Core27 skin weights plus face blendshapes; the existing TRELLIS path returns an unrigged textured GLB and its automatic skin fit does **not** create facial controls. Staging the kiss through neck/head aim, jaw/lip shapes, blink, and a short contact hold is an implementation recommendation based on the missing channels, not a claim that ARDY generated facial acting. The original workspace’s `docs/CHARACTERS.md` describes these limits; [TRELLIS](https://github.com/microsoft/TRELLIS) is the source project for the mesh generator.

## Existing GPU and cost

Read-only `nvidia-smi` over the existing SSH connection reported an RTX 6000 Ada with **49,140 MiB total, 33,039 MiB used, 15,473 MiB free** at the check. G1 and Core/InterGen Python processes used 15,882 and 17,142 MiB respectively; the character HTTP server was running. The three Core probes completed through that warm worker in 0.99–1.11 s client round trip per 80-frame clip. No service was stopped, restarted, or provisioned. This free VRAM supports the present bounded Core calls; it is not a safe budget for another resident large model without a new memory test.

`runpodctl pod list` could not identify the account's actual hourly charge because no RunPod API key was configured locally. RunPod's public pricing page currently displays **$0.84/hour** for an RTX 6000 Ada Pod, but the actual existing Pod's rate, storage and billing type remain unverified. The prototype adds **no extra Pod**. [RunPod public pricing](https://www.runpod.io/pricing).

## Recorded integration result

The independent [run verifier](../experiments/verify_swing_run.py) checked the saved browser run at `.runtime/swing/20260926-060750-a5d6d8/` against its **7,600 recorded** 60 Hz frames and 126.566-second WebM, rather than later server frames that continued to log. Its `verification.json` passed the ordered seven-command sequence, live Core refreshes, joint continuity, bone lengths, carry grips, end roof support, and sampled city/web clearance. Maximum observed joint step was 0.142 m per tick; maximum active carry grip error was 9.0 mm. Five samples per body bone found a maximum 0.038 m conservative AABB overlap; the web samples found none outside source-mesh-derived terminal allowances of 0.503–0.755 m at their anchor buildings. Both characters' final toes were within the destination building footprint and 0.083–0.101 m from the chosen roof plane. The checks are geometric proxies over selected samples, not a certificate of continuous mesh collision avoidance or force-based support. [Verifier tests](../test_verify_swing_run.py) cover a corrupted bone, an arm-only obstacle, a web crossing, and the command sequence.
